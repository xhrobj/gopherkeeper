# ⚖️ Требования и ограничения GophKeeper

Этот документ содержит принятые требования, проектные ограничения и границы реализации GophKeeper. Официальное техническое задание Практикума остаётся главным источником требований: [📝 `SPECIFICATION.md`](SPECIFICATION.md).

Инструкция по локальному запуску находится в [🤓 полном руководстве по настройке и запуску](SETUP.md). Краткий сценарий запуска описан в [🚀 гайде по быстрому запуску](SETUP_QUICK.md).

## Архитектура

GophKeeper состоит из Сервера и Клиента.

Сервер хранит пользователей и зашифрованные записи в PostgreSQL и одновременно предоставляет HTTPS и gRPC API поверх общей бизнес-логики. Оба транспорта используют TLS и работают с одной базой данных. Режим запуска только одного транспорта не поддерживается. Если один транспорт аварийно завершает работу, Сервер корректно останавливает второй и завершает процесс целиком.

Клиент предоставляет отдельные CLI-команды и TUI поверх общих application use cases, сохраняет локальную online-сессию и использует зашифрованный SQLite-кеш для offline-доступа только для чтения.

HTTP-контракт описан в [OpenAPI-спецификации](../api/openapi.yaml).

## Конфигурация Сервера

| Параметр          | Источник                               | Значение                                               |
| ----------------- | -------------------------------------- | ------------------------------------------------------ |
| HTTPS address     | `ADDRESS`, `--address`, `-a`           | `localhost:8080`                                       |
| gRPC address      | `GRPC_ADDRESS`, `--grpc-address`, `-g` | `localhost:50051`                                      |
| PostgreSQL DSN    | `DATABASE_DSN`, `--database-dsn`       | обязательный                                           |
| TLS certificate   | `TLS_CERT_FILE`, `--tls-cert`          | обязательный                                           |
| TLS private key   | `TLS_KEY_FILE`, `--tls-key`            | обязательный                                           |
| JWT secret        | `JWT_SECRET`                           | обязательный                                           |
| JWT TTL           | `JWT_TTL`, `--jwt-ttl`                 | `15m`                                                  |
| Record master key | `RECORD_MASTER_KEY`                    | обязательный                                           |
| Record key ID     | `RECORD_KEY_ID`                        | `primary`                                              |
| Log level         | `LOG_LEVEL`                            | `info`                                                 |

`JWT_SECRET` и `RECORD_MASTER_KEY` должны быть разными. Значений по умолчанию для этих секретов нет: без них Сервер не запускается.

## Конфигурация Клиента

JSON-конфиг Клиента содержит:

| Поле           | Назначение                              |
| -------------- | --------------------------------------- |
| `transport`    | выбранный транспорт: `https` или `grpc` |
| `address`      | адрес HTTPS API                         |
| `grpc_address` | адрес gRPC API                          |
| `ca_cert_file` | дополнительный доверенный CA-сертификат |
| `session_dir`  | каталог локальной online-сессии         |
| `cache_dir`    | базовый каталог локальных кешей         |

Клиент использует адрес выбранного транспорта. Автоматического переключения между HTTPS и gRPC нет.

### Источники конфигурации

| Назначение        | JSON           | Флаг                   | Env            |
| ----------------- | -------------- | ---------------------- | -------------- |
| Путь к конфигу    | —              | `--config`, `-c`       | `CONFIG`       |
| Транспорт         | `transport`    | `--transport`          | `TRANSPORT`    |
| HTTPS address     | `address`      | `--address`, `-a`      | `ADDRESS`      |
| gRPC address      | `grpc_address` | `--grpc-address`, `-g` | `GRPC_ADDRESS` |
| CA certificate    | `ca_cert_file` | `--ca-cert`            | `CA_CERT_FILE` |
| Session directory | `session_dir`  | `--session-dir`        | `SESSION_DIR`  |
| Cache directory   | `cache_dir`    | `--cache-dir`          | `CACHE_DIR`    |

Приоритет источников:

```text
flag > env > config file > default
```

Если путь к JSON-конфигу передан явно, но файл отсутствует, содержит некорректный JSON, неизвестные поля или недопустимое значение, Клиент завершает запуск ошибкой.

При запуске TUI с `--config` или `CONFIG` окно `System → Config...` сохраняет изменения в тот же JSON-файл. Без переданного пути изменения действуют только до завершения текущего процесса.

## Локальные данные Клиента

Если `session_dir` не задан, online-сессия хранится по пути:

```text
<user-cache-dir>/gopherkeeper/session.json
```

Если `cache_dir` не задан, зашифрованный SQLite-кеш каждого аккаунта хранится по пути:

```text
<user-cache-dir>/gopherkeeper/cache/<account-id>/cache.db
```

`account-id` не зависит от адреса Сервера и выбранного транспорта. Изменение адреса или переключение между HTTPS и gRPC не создаёт новый кеш для того же login.

Отдельный стабильный идентификатор Сервера не хранится. При подключении к разным независимым Серверам необходимо использовать разные конфиги, `session_dir` и `cache_dir`.

## Синхронизация и offline-режим

Сервер является источником актуального состояния.

Синхронизация запускается только явно: Клиент добавляет в кеш новые серверные записи, обновляет записи с изменившейся `revision` и удаляет записи, отсутствующие на Сервере. Offline-кеш не содержит несохранённых локальных изменений.

Offline-режим позволяет только просматривать ранее синхронизированные записи. Создание, изменение, удаление и фоновая синхронизация не поддерживаются. Данные отражают состояние Сервера на момент последней успешной синхронизации.

## Сборочная информация

В Клиент и Сервер через `ldflags` встраиваются версия, дата сборки и commit. При отсутствии значения используется безопасное значение по умолчанию.

Клиент собирается для Linux, Windows и macOS.

## Требования к учётным данным

### Login

* длина от 3 до 32 ASCII-символов;
* допускаются латинские буквы, цифры и символы `.`, `_`, `-`;
* первый символ должен быть латинской буквой или цифрой;
* пробельные символы в начале и конце удаляются;
* заглавные латинские буквы приводятся к нижнему регистру;
* пробельные и Unicode-символы внутри login не допускаются.

Примеры допустимых login:

```text
bob
alice
bob_42
eve.dev
king-of-andals
```

### Password

При регистрации:

* длина от 8 до 64 символов;
* допускаются печатные ASCII-символы от `!` до `~`;
* пробелы, табуляция, переносы строк и Unicode-символы не допускаются;
* значение чувствительно к регистру;
* значение не обрезается и не нормализуется.

Пример допустимого password:

```text
correct-horse-battery-staple
```

При аутентификации политика минимальной длины повторно не применяется: учётные записи, созданные ранее с более коротким password, продолжают работать.

## Типы записей и ограничения данных

GophKeeper поддерживает записи типов `credentials`, `card`, `text` и `binary` через единый CRUD. Тип после создания не изменяется, начальная `revision` равна `1`.

| Поле                   | Ограничение                                |
| ---------------------- | ------------------------------------------ |
| `title`                | 1–255 Unicode-символов, single-line        |
| credentials `login`    | 1–255 Unicode-символов, single-line        |
| credentials `password` | 1–255 Unicode-символов, single-line        |
| credentials `url`      | 0–255 Unicode-символов, single-line        |
| `metadata`             | не более 255 Unicode-символов, single-line |
| card `number`          | 12–20 ASCII-цифр                           |
| card `cardholder`      | не более 25 Unicode-символов               |
| card `expiry_month`    | `1..12`                                    |
| card `expiry_year`     | `0..99`                                    |
| card `cvv`             | при наличии ровно 3 ASCII-цифры            |
| text `text`            | не более 1 МиБ UTF-8                       |
| binary `filename`      | 1–255 Unicode-символов                     |
| binary `data`          | не более 2 МиБ после Base64-декодирования  |
| HTTP request body      | не более 4 МиБ                             |

Номер карты содержит только ASCII-цифры и хранится в нормализованном виде. Проверка банка, платёжной системы и фактической действительности карты не выполняется.

## Конкурентные изменения

Записи используют оптимистическую блокировку через `revision`.

При обновлении и удалении Клиент передаёт ожидаемую ревизию через `If-Match` или эквивалентное поле выбранного транспорта. Операция выполняется только при совпадении ожидаемой и текущей ревизий.

Успешное обновление атомарно изменяет `updated_at`, увеличивает `revision` на 1 и возвращает новую ревизию.

При устаревшей ревизии возвращается конфликт. Автоматического merge нет, и конфликт не должен приводить к молчаливой перезаписи данных.

История предыдущих версий записи не хранится.

## Модель безопасности

HTTPS и gRPC используют TLS. Password пользователей хешируются через bcrypt, авторизация выполняется через JWT.

Приватные payload записей, включая `metadata`, шифруются на Сервере через AES-256-GCM.

Локальный кеш шифруется через AES-256-GCM ключом, полученным из password с помощью Argon2id.

Профиль Argon2id v1:

* `time = 3`;
* `memory = 64 MiB`;
* `parallelism = 4`;
* длина ключа — 32 байта;
* длина соли — 16 байт.

Это не end-to-end encryption: Сервер получает plaintext внутри защищённого соединения и обрабатывает его в памяти.

Открытыми остаются:

* `title`;
* ID;
* type;
* revision;
* даты создания и изменения;
* служебные криптографические поля.

В логи запрещено записывать:

* password пользователей;
* bearer token;
* приватные payload;
* ключи шифрования;
* полный номер карты и CVV;
* plaintext локального кеша.

## Ограничения TUI

Чувствительные поля по умолчанию скрыты.

Встроенный file/folder picker ограничен каталогом запуска Клиента и его подкаталогами. Переход выше этого каталога запрещён. Picker предназначен для локальных файлов и каталогов и не выполняет дополнительную проверку символических ссылок и специальных объектов файловой системы.

Для доступа к нужным файлам Клиент следует запускать из каталога, содержащего эти файлы или их родительский каталог.

## Известные ограничения

Не поддерживаются:

* большие файлы, streaming, chunking и resumable upload;
* OTP;
* KMS, envelope encryption и ротация мастер-ключей;
* SQLCipher и системные keyring-хранилища.

## Тестирование и CI

Общее покрытие проекта должно быть не ниже 70%, Coverage on New Code в SonarCloud — не ниже 80%.

Проект проверяется unit-, integration- и end-to-end тестами, race detector и CI. CI также проверяет линтинг, сборку Сервера, кроссплатформенную сборку Клиента и OpenAPI.

Основные команды проверки и сборки приведены в [🤓 руководстве по настройке и запуску](SETUP.md).
